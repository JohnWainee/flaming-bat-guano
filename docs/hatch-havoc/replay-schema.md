# Hatch Havoc — Deterministic Replay Schema (v1)

**Status:** Milestone 0 deliverable (PRD v1.1 §35 step 10; requirements per
§20.5, §24.3)
**Reference implementation:** `prototype/gamecore-reference/gamecore/replay.py`
**Conformance suite:** `prototype/gamecore-reference/golden/*.json`

A replay record fully reproduces a run on any conforming implementation, on
any device — bit-for-bit. There is deliberately **no timing data anywhere**
in the schema: the game model is shot-indexed (PRD §6.2), so wall-clock and
frame timing cannot influence outcomes.

## Record format

```jsonc
{
  "schemaVersion": 1,                  // this document's version
  "rulesetVersion": "0.1.0",           // gameplay rules version (gameplay-rules.md)
  "levelId": "ref-001-first-clutch",   // level definition id
  "seed": 12345,                       // PCG32 seed for the run
  "actions": [                         // ordered player actions
    {"type": "shot", "dx": -196608, "dy": -65536}
  ],
  "expected": {                        // present in golden vectors / submissions
    "finalHash": "b2d514…",            // sha256 canonical state hash (64 hex chars)
    "score": 270,
    "shots": 3,
    "status": "active"                 // active | won | lost
  }
}
```

## Actions

Ruleset 0.1.0 defines one action type:

- `shot` — aim vector `dx`, `dy` as **raw Q16.16 integers** (`dy < 0`).
  Invalid actions (zero vector, `dy ≥ 0`, or a shot after the run ended) make
  the record malformed; verifiers reject the record rather than skipping the
  action.

Future action types (`swap`, `useSpecial`, assist toggles) extend this list
under a schema/ruleset bump.

## Canonical state hash

sha256 over canonical JSON — **sorted keys, separators `,` and `:`, no
whitespace, UTF-8** — of the full logical state:

`rulesetVersion, levelId, seed, shots, status, score, combo, parity, rows,
insertionCountdown, currentEgg, nextEgg, rngState, rngInc`

(exact field names and types: `replay.canonical_state`). Any port must
serialize identically; the hash, not the serialization, is what is stored
and compared.

## Uses

1. **Debugging:** every playtest build records the active run's replay;
   a board-corruption report is reproducible from the record alone.
2. **Golden conformance (PRD §24.3):** `golden/*.json` are generated by the
   reference core; the Swift GameCore CI must replay each record and match
   `expected` exactly. Any divergence is a release blocker.
3. **Leaderboard submissions (PRD §15.3):** a ranked submission carries its
   replay record (minus `expected`, plus the claimed score). At launch,
   validation is client-side sanity checking only; the record format is what
   makes optional post-launch server-side verification possible without
   client rework (PRD §31.2).

## Versioning rules

- Any change that alters any golden `finalHash` is a **ruleset** bump
  (`RULESET_VERSION`), even if the schema shape is unchanged.
- Any change to record structure is a **schema** bump.
- Daily Eruption seeds are pinned to a ruleset version at publication
  (PRD §8.4); a verifier must refuse to score a record whose
  `rulesetVersion` it does not implement.
